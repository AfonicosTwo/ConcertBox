1. Elección del proyecto y problemática que resuelve
En la actualidad, la industria de la música en vivo ha experimentado una inflación significativa, convirtiendo la asistencia a conciertos en una inversión considerable de tiempo y dinero para el usuario. A pesar de esto, existe una alta desinformación previa a la compra del boleto. Los consumidores carecen de una plataforma centralizada y confiable donde puedan consultar reseñas reales sobre la calidad de una gira actual, la acústica y logística de recintos específicos, o el setlist aproximado que un artista está interpretando.
Adicionalmente, los fanáticos de la música no cuentan con una red social o bitácora digital especializada (similar al nicho que atiende Letterboxd en el cine o Goodreads en la literatura) que les permita catalogar, clasificar y documentar su historial de asistencia a eventos en vivo mediante un perfil unificado. Esta "fragmentación de la memoria" musical impide que el usuario tenga un registro histórico de sus experiencias culturales y comparta recomendaciones valiosas con la comunidad.

2. Objetivo del desarrollo
Objetivo General
Diseñar y desarrollar una plataforma web interactiva basada en una arquitectura Cliente-Servidor que funcione como una bitácora y red de reseñas de conciertos en vivo. El sistema permitirá a los usuarios registrar los eventos a los que han asistido, otorgar calificaciones, escribir reseñas y visualizar métricas de su consumo musical.
Objetivos Técnicos Específicos
●	Consumo de APIs Externas: Implementar la integración de tres APIs de terceros (Ticketmaster para eventos futuros, Setlist.fm para listas de canciones históricas y Spotify para metadatos de artistas) para automatizar la carga de información oficial.
●	Persistencia de Datos: Construir un backend robusto con Node.js que gestione un sistema CRUD completo para la creación de perfiles de usuario, autenticación y almacenamiento de interacciones sociales.
●	Interfaz Dinámica: Desarrollar un frontend responsivo que consolide datos en tiempo real, ofreciendo una experiencia de usuario fluida y visualmente atractiva para la exploración de eventos.
●	Gestión de Contenido Multimedia: Permitir que los usuarios suban y organicen fotografías de sus experiencias para enriquecer el historial visual de cada evento.

3. Tipo de sitio y justificación técnica
El tipo de sitio elegido para este proyecto es una Aplicación Web de Una Sola Página (SPA - Single Page Application) desarrollada con el framework Next.js / React. Esta elección se justifica por las siguientes necesidades críticas del proyecto:
Factor	Justificación Técnica
 
Interactividad Dinámica	Al funcionar como una red social (likes, reseñas, filtros), el uso de React permite que la interfaz se actualice de forma instantánea sin recargar toda la página, mejorando la experiencia del usuario (UX).
Consumo de APIs	La arquitectura de Next.js facilita el manejo de peticiones asíncronas hacia las APIs de Ticketmaster y Spotify, permitiendo que los datos se rendericen de manera eficiente.
Escalabilidad	El desarrollo modular por componentes permitirá añadir funciones futuras (como mapas interactivos o sistemas de mensajería) sin comprometer la estructura base del código.
SEO y Rendimiento	Next.js ofrece renderizado del lado del servidor (SSR), lo cual es vital para que las reseñas y perfiles de artistas sean indexados correctamente por los motores de búsqueda.
Esta arquitectura es la más conveniente según la problemática planteada, ya que el usuario requiere un sistema ágil para consultar información de conciertos en tiempo real, donde la velocidad de carga y la fluidez de la navegación son determinantes para la retención del usuario en la plataforma.

5. Principios de UX/UI a seguir en ConcertBox
Para garantizar que la plataforma sea intuitiva, accesible y retenga a los usuarios, el desarrollo de ConcertBox se fundamentará en los siguientes principios de Experiencia de Usuario (UX) e Interfaz de Usuario (UI):
•	Estética en Dark Mode: Al tratarse de una aplicación orientada a la industria musical y el entretenimiento nocturno, la interfaz utilizará una paleta de colores oscuros basándose principalmente en negros y grises profundos. Esto no solo reduce la fatiga visual del usuario, sino que genera un alto contraste que permite que las fotografías de los conciertos y los colores de los botones o las calificaciones destaquen inmediatamente, mejorando la legibilidad.
•	Diseño Centrado en el Usuario: La arquitectura de la información estará diseñada para minimizar el esfuerzo del usuario al momento de registrar un concierto o evento. Se implementarán selectores visuales atractivos para que el proceso de escribir una reseña sea ágil y no requiera una carga cognitiva alta.
•	Jerarquía Visual: Para no abrumar al usuario con demasiada información, la pantalla de inicio y los perfiles de artistas respetarán una estricta jerarquía visual. Se utilizarán tipografías de gran peso y contenedores de imágenes para guiar la vista del usuario desde lo más importante como los artistas y las calificaciones, hacia los detalles secundarios como las setlist o las reseñas de terceros.

11. Stack tecnológico elegido para la parte del BackEnd.
Para la construcción de la lógica de negocio y la gestión de datos de ConcertBox, se implementará una arquitectura basada en el entorno de JavaScript, logrando así un desarrollo unificado (Full-Stack JS) que se comunicará de forma nativa con el FrontEnd previamente desarrollado.

El Stack tecnológico se compone de los siguientes elementos y bibliotecas:

Entorno de Ejecución: Node.js. Permitirá ejecutar código JavaScript del lado del servidor de manera asíncrona y eficiente.

Framework Web: Express.js. Se utilizará para levantar el servidor, enrutar las peticiones HTTP y estructurar la API RESTful de manera minimalista y escalable.

Base de Datos y ODM: MongoDB como motor de base de datos NoSQL, complementado con el paquete Mongoose (Object Data Modeling) para esquematizar los datos y facilitar las consultas.

Seguridad y Criptografía: El paquete Bcrypt.js para aplicar algoritmos de hashing a las contraseñas, y el estándar JWT (JSON Web Tokens) a través del paquete jsonwebtoken para la generación de credenciales de acceso.

Peticiones a Terceros: La biblioteca Axios para gestionar de forma optimizada las solicitudes asíncronas hacia las APIs externas (Ticketmaster, Setlist.fm y Spotify) desde el servidor.

Variables de Entorno: El módulo Dotenv para proteger las cadenas de conexión y las llaves secretas (API Keys) fuera del código fuente.

12. Elementos necesarios para el BackEnd
a)	Bases de Datos

El manejador seleccionado es MongoDB, desplegado en la nube a través de MongoDB Atlas. La justificación de esta elección NoSQL radica en su naturaleza orientada a documentos (formato BSON/JSON), la cual ofrece la flexibilidad ideal para almacenar las "Reseñas" y el "Muro de Boletos" de los usuarios. Al ser datos que pueden variar en estructura, algunos conciertos tendrán vibe tags, otros tendrán fotografías adjuntas, MongoDB permite una escalabilidad horizontal superior a las bases de datos relacionales tradicionales como MySQL para este caso de uso.

b)	Seguridad

La plataforma implementará seguridad en dos capas principales. En el almacenamiento, se utilizará Bcrypt para encriptar las contraseñas antes de guardarlas, asegurando que ni siquiera los administradores de la base de datos puedan leerlas en texto plano. En el transporte y acceso, se configurará el middleware CORS (Cross-Origin Resource Sharing) en Express para asegurar que el BackEnd únicamente acepte peticiones web provenientes del dominio oficial del FrontEnd de ConcertBox, bloqueando solicitudes externas maliciosas.

c)	Uso de APIs, REST, servicios, controladores y CRUD

El BackEnd se estructurará bajo el patrón MVC (Modelo-Vista-Controlador) adaptado a una arquitectura de microservicios:

•	APIs y Servicios: El servidor de Node.js actuará como intermediario para consultar las APIs de Ticketmaster y Spotify. Esto oculta las llaves de acceso (API Keys) del navegador del cliente y permite formatear los datos de los artistas antes de enviarlos a la vista.

•	Controladores y REST: Se desarrollará una API REST propia con rutas semántica. Cada ruta estará delegada a un "Controlador" específico que contendrá la lógica de negocio.

•	CRUD e Interacción: Se programarán las operaciones completas de creación, lectura, actualización y eliminación. 

d)	Autenticación

•	El control de sesiones no utilizará cookies tradicionales, sino Autenticación basada en tokens con JWT (JSON Web Tokens). El flujo será el siguiente: El usuario envía sus credenciales.

•	El BackEnd las valida contra la base de datos en MongoDB.

•	Si son correctas, el servidor firma y emite un JWT que contiene la identidad encriptada del usuario. 

•	El FrontEnd almacena este token y lo adjunta en la cabecera HTTP, cada vez que intente realizar una acción protegida como interactuar con el Modal de Reseña. El servidor validará la firma del token antes de procesar la acción.

e)	Otros

Para asegurar la calidad del BackEnd, se integrará la plataforma Postman como herramienta de testeo y documentación de endpoints durante el desarrollo. Esto permitirá verificar rigurosamente que las rutas devuelvan los códigos de estado HTTP adecuados (200 OK, 400 Bad Request, 401 Unauthorized, 404 Not Found) antes de conectarlas con el código de la interfaz de usuario en Next.js.
